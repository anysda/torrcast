# Этап 6 — подключение к реальному ТВ: только сеть и конфиг

Стенду добавлена вторая нога в `192.168.100.0/24`, в конфиг прописан адрес ТВ.
**Каста не было.** К `192.168.100.102` за весь этап не ушло ни одного пакета: ни ping,
ни коннекта на `:8009`, ни discovery. Живой тест делает владелец — раздел
[«Инструкция владельцу»](#инструкция-владельцу--живой-тест) ниже.

## 1. Вторая нога: параметры

| Что | Значение |
|---|---|
| Интерфейс | `net1` → `eth1` в контейнере |
| Мост | `vmbr100` на caffeine (в нём `vxlan100`, VNI 100, и `veth101i1` от [[kinocast]]) |
| Адрес | **`192.168.100.62/24`**, статика |
| MTU | **1450** — иначе пакеты крупнее 1422 Б полезной нагрузки молча теряются в VXLAN |
| Шлюз | **нет и не должно быть** (см. ниже) |
| MAC | `BC:24:11:5D:BD:84` (выдан Proxmox) |
| Первая нога | без изменений: `eth0 = 192.168.1.62/24`, gw `192.168.1.1` |

**Почему на `net1` нет шлюза.** Шлюз на второй ноге перебил бы default route, и стенд
потерял бы LAN с интернетом (а вместе с ними — Prowlarr, TorrServer и доставку серта).
Маршрут в `.100.0/24` появляется сам как connected-маршрут по адресу и маске. Ровно так
же сделано у [[kinocast]] (CT101) — образец, по которому нога и повторена.

**Почему адрес `.62`.** Свободность определена **по докам и конфигам, а не сканированием**
(в сегменте живёт телевизор): заняты `.1` VyOS, `.2` kinocast, `.5` zapret2, `.10` UniFi,
`.100` точка Nano HD, `.102` ТВ (static-mapping в DHCP VyOS, MAC `00:7d:3b:15:b1:2c`).
DHCP-пул VyOS — `.100`–`.200`, поэтому статика взята **ниже пула** и совпадает по
последнему октету с LAN-адресом стенда (`192.168.1.62` ↔ `192.168.100.62`) — так проще
не перепутать. Сверено по `pct config`/`qm config` **обеих** нод, `infra/Network.md`,
`gitops/nicotine/roles/vyos_rtr` и живому конфигу VyOS.

### Рецепт воспроизведения

Роли для стенда в gitops нет (стенд временный, после приёмки его заменяет прод-LXC в
диапазоне 1xx), поэтому воспроизведение — одна строка на caffeine:

```bash
pct set 501 -net1 name=eth1,bridge=vmbr100,ip=192.168.100.62/24,mtu=1450,type=veth
```

Нога поднимается **горячим включением, без перезагрузки** контейнера. `protection=1`
снимать не требуется. Для прод-LXC этапа «после приёмки» те же параметры кладутся в
роль как второй элемент списка интерфейсов.

## 2. Проверка связности — без единого пакета в адрес ТВ

Проверялись только не-ТВ адреса сегмента: `.100.1` (br100 у [[vyos-rtr]], живёт на
**другой** ноде — то есть проверяется и сам VXLAN) и `.100.2` ([[kinocast]], та же
нода, локальный мост).

```
$ ip route
default via 192.168.1.1 dev eth0 onlink          ← остался на месте
192.168.1.0/24   dev eth0 proto kernel src 192.168.1.62
192.168.100.0/24 dev eth1 proto kernel src 192.168.100.62

$ ping -c3 192.168.100.1     → 0% loss, avg 0.469 ms   (через VXLAN на nicotine)
$ ping -c3 192.168.100.2     → 0% loss, avg 0.061 ms   (kinocast, локально)
```

**MTU держится ровно 1450** — доказано с двух сторон, а не «настроено»:

```
$ ping -M do -s 1422 192.168.100.1   → 1430 bytes from … 0.465 ms   (1422+8+20 = 1450)
$ ping -M do -s 1423 192.168.100.1   → ping: local error: message too long, mtu=1450
```

**После `pct reboot 501`** обе ноги, MTU и default route на месте, split-DNS
(`torrcast.anysda.space` → `192.168.1.62`), интернет (`github 200`) и
`torrcast-cert-pull.timer` — живы.

**Телевизор не тронут:** в таблице соседей стенда `192.168.100.102` отсутствует
(`ip neigh | grep -c 192.168.100.102` → `0`) — за весь этап адрес ни разу не
резолвился в MAC, то есть к нему не отправлялось вообще ничего.

## 3. Путь данных: поток пойдёт не по этой ноге

Это важно понимать до живого теста. Нога в `.100` нужна **только для управляющего
канала** — pychromecast со стенда стучится на `192.168.100.102:8009`. Из LAN в
`.100.0/24` маршрута нет вовсе (сегмент за NAT VyOS), без ноги каст был бы невозможен.

**Сам HLS-поток идёт другим путём.** ТВ получает URL по имени
`https://torrcast.anysda.space:8443`, резолвер сегмента (`.100.1` → [[adguard]]) отдаёт
**`192.168.1.62`** — LAN-адрес стенда. Значит ТВ тянет сегменты через NAT VyOS, а не
напрямую с `.100.62`.

Путь проверен, и **тоже без ТВ**: временным `/32`-маршрутом трафик со стенда пущен с
исходником `192.168.100.62` через `.100.1` на LAN-хост — `HTTP 200 за 0.038 с`
(маршрут после проверки снят, таблица чистая). То есть клиент сегмента до LAN-адреса
стенда доходит, и на живом тесте ТВ заберёт манифест.

Лишний хоп из дома не выходит (§1 «ноль облака» не нарушен), а на 12.5 Мбит/с пика
роутер не заметит нагрузки. Убрать хоп можно только подменой имени в DNS-форвардере
VyOS на `192.168.100.62` — это правка VyOS, на этом этапе она не санкционирована.

## 4. Конфиг стенда

```
$ cast --tv 192.168.100.102
ТВ: 192.168.100.102
```

```diff
-  "receiver": "mock",
-  "tv": "mock"
+  "receiver": "chromecast",
+  "tv": "192.168.100.102"
```

Команда безопасна по построению: `_cmd_configure` только пишет конфиг. **Проверено по
коду, что приёмника не касаются и остальные команды:** `make_receiver` вызывается
ровно в одном месте — внутри `_play`, то есть уже в юните показа. `cast status` читает
конфиг, состояние и systemd; `cast stop` — только systemd; `--dry` возвращается раньше
`_play`. `ChromecastReceiver` соединяется лениво (`_device()` из `play`/`position`), и
конструктор соединения не открывает.

`cast status` после правки конфига выполнен — «ничего не играет», код 0, соединения нет.
`pychromecast` на стенде установлен и импортируется (проверено импортом, не кастом).

## 6. Если стенд пересоздаётся

Пересоздание CT501 — и позже переезд на прод-LXC — обнуляет ровно две вещи, которых
нет ни в `install.sh`, ни в ролях: **вторую ногу** (это параметр контейнера, а не
гостевой конфиг) и **ключ доставки серта** (он рождается на самой машине). Порядок
работ, чтобы не выяснять это заново:

1. LXC по параметрам из [stage5](stage5.md#стенд): Debian 12 unprivileged, 4 vCPU /
   8 ГиБ, `192.168.1.62/24`, nameserver `192.168.1.57`, `onboot=0`, `protection=1`.
2. Провижининг хоста (это не установка torrcast): ssh-ключи флота и пароль root, `git`,
   read-only deploy key проекта `anysda/torrcast` в GitLab, выключенный IPv6.
3. Вторая нога — ниже.
4. Серт LE — три шага, ниже. **До** `install.sh`: иначе фаза `https` положит
   самоподписанный, и «телевизор не играет» уведёт в отладку показа, а не серта.
5. `git clone … && ./install.sh && cast --tv 192.168.100.102` — около четырёх минут.

Split-DNS (`torrcast.anysda.space` → `192.168.1.62`) пересоздание переживает сам: запись
живёт в `gitops/nicotine` и привязана к адресу, а не к машине. Меняется адрес — правится
там, руками в AdGuard нельзя (роль кладёт `AdGuardHome.yaml` шаблоном целиком).

### Вторая нога — одна строка на caffeine

```bash
pct set 501 -net1 name=eth1,bridge=vmbr100,ip=192.168.100.62/24,mtu=1450,type=veth
```

`gw=` не задавать намеренно (§1: шлюз на этой ноге перебил бы default route и унёс бы
интернет вместе с доставкой серта). `mtu=1450` обязателен — под ним VXLAN. Нога встаёт
горячим включением, `protection=1` снимать не нужно. Проверка — §2: `ip route`,
`ping 192.168.100.1` и `.2`, `ping -M do -s 1422` против `-s 1423`. **В `.102` не
стучать** — телевизор будит любой коннект.

### Серт LE — три шага, порядок обязателен

Ключ доставки родится новым, а прописан он на ингрессе — одним прогоном не обойтись.
Разбор: `gitops/cloud/docs/torrcast-cert.md`, раздел «Порядок первого заведения».
Выполняется из `~/homelab/gitops/cloud`:

```bash
# 1. Стенд: раскладка и рождение ключа. Тянуть ещё нечем — прогон выключаем.
ansible-playbook playbooks/torrcast-cert.yml -e torrcast_cert_pull_now=false
#    Плей напечатает готовый кусок для host_vars ингресса.

# 2. Ингресс: вписать напечатанное в inventory/host_vars/vps-home-ingress.yml
#    (ingress_cert_pull_clients) и применить.
ansible-playbook playbooks/ingress.yml --check --diff   # посмотреть, что будет
ansible-playbook playbooks/ingress.yml

# 3. Стенд: теперь доставка проходит. Плей сам проверяет файлы на диске.
ansible-playbook playbooks/torrcast-cert.yml
```

Сам сертификат перевыпускать не нужно: он живёт в `acme.json` ингресса и пересоздания
дома не замечает — стенд просто забирает его заново. Зато ключ **мёртвой** машины с
ингресса надо снять: два прогона `playbooks/ingress.yml` — сначала `state: absent` у
старой записи, потом удаление самой записи (процедура обкатана 05-08-2026).

## Инструкция владельцу — живой тест

Всё готово: нога в сети ТВ есть, адрес ТВ в конфиге, приёмник переключён на
`chromecast`. Осталось нажать. **Телевизор проснётся сам** от каста — включать вход
руками не нужно.

### Что выполнить

```bash
ssh root@192.168.1.62
cast моана 2
```

Дальше три вопроса, у каждого разумный дефолт в скобках — **можно просто трижды нажать
Enter**: какую картину, какой релиз, какую дорожку.

### Что увидишь и сколько ждать

| Шаг | Ожидание |
|---|---|
| после последнего Enter | строка `▶ «Моана 2» · дорожка 1 → ТВ   (старт NN с)` |
| картинка на ТВ | **15–30 с** от последнего Enter (§3.1: DHT + буфер + запуск приёмника) |
| второй запуск того же (resume) | **5–15 с**, вопросов не задаёт |

Пауза и перемотка — **пультом телевизора**, это штатный media receiver.

```bash
cast status    # что играет, позиция/длительность, дорожка, приёмник
cast stop      # снять каст и запомнить позицию
```

Хочешь проверить возобновление: `cast stop` посреди фильма, потом снова `cast моана 2`
— спросит «Продолжить? [Да/сначала]». Сериал с уже сохранённой позицией под рукой:
`cast киберпанк` продолжит s1e5 с 0:18:39 без единого вопроса.

### Что считать успехом

- [ ] на ТВ появилась **картинка** (не чёрный экран, не `LOAD ERROR`)
- [ ] есть **звук**, и он на выбранной дорожке (русский дубляж по умолчанию)
- [ ] `cast status` показывает **растущую позицию**, а не нули
- [ ] перемотка пультом работает, шкала на месте
- [ ] `cast stop` **гасит** показ, ТВ возвращается к себе
- [ ] после `stop` повторный запуск продолжает **с той же секунды**

### Если что-то пошло не так

```bash
journalctl -u torrcast-play -n 100 --no-pager     # журнал показа: ffmpeg, сторож, приёмник
journalctl -u torrcast-play -f                    # то же вживую
cast stop                                        # всегда безопасно, гасит всё
```

Что писать мне: **строку ошибки от `cast`** (она одна и по-русски) плюс хвост
`journalctl`. По ним видно, на чём именно споткнулись — на поиске, на раздаче, на
упаковке или на самом телевизоре.

Типичные подозреваемые, если картинки нет:

| Симптом | Скорее всего |
|---|---|
| `ТВ 192.168.100.102 не принял каст` | ТВ выключен из розетки / не в сети `.100` / занят другим кастом |
| ТВ проснулся, но экран чёрный и через минуту вернулся к себе | ресивер не принял поток — смотреть `stream_type` и кодек (см. риски) |
| `показ не запустился` | легло что-то на стенде (TorrServer/Prowlarr/ffmpeg) — `journalctl` |
| долго, но потом играет | мало сидов на релизе; следующий раз выбрать релиз с бо́льшим числом сидов |

## Известные нерешённые риски

Честно, до живого теста это не проверить ничем:

1. **Ветка `ChromecastReceiver` ни разу не исполнялась.** Весь код каста написан и
   покрыт типами, но ни одна его строка не выполнялась против живого устройства — ТВ
   не трогали принципиально. Первый запуск владельца и есть её первое исполнение.
2. **`stream_type: BUFFERED` выбран умозрительно.** Манифест у нас `EVENT` (только
   дописывается), и `BUFFERED` даёт шкалу и перемотку пультом. Если ресивер откажется —
   это одно слово на `LIVE` в `torrcast/cast.py`.
3. **HEVC на Q70D неизвестен.** Дефолтом всегда идёт H.264 (настоящий кодек читается
   `ffprobe` из потока, а не из имени релиза), HEVC-релизы помечены `⚠` и дефолтом не
   становятся — так что на риск можно наступить только вручную.
4. **Путь данных через NAT VyOS** (§3 выше) проверен по маршруту и портам, но не
   реальным телевизором: DNS сегмента отдаёт ТВ LAN-адрес стенда, а не `.100.62`.
5. **Битрейт и диалект HLS** закрыты на mock (пик 12.5 Мбит/с против потолка ~20, TS ~4 с,
   `EVENT`, CORS, доверенный LE) — но подтверждение, что это ест **именно** Q70D,
   опирается на то, что kinocast отдаёт этому же телевизору тот же диалект уже год.
