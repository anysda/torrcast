# Этап 3 — прогресс: transient-юнит, сторож, resume, порог 95 %

Приёмка §7.3: показ живёт в юните и переживает выход `cast`; позиция снимается с
приёмника и ложится в `state.json`; `cast <запрос>` продолжает с сохранённого места;
95 % длительности = «досмотрено»; `stop`/`status` честны, юнит не течёт. Всё на
mock-приёмнике, на agent-ops, на `127.0.0.1`. ТВ, стенд, caffeine, AdGuard, CT302 и
сеть `192.168.100.0/24` не трогались.

## Что сделано

| Слагаемое | Где | Суть |
|---|---|---|
| Transient-юнит | `stream.start_play_unit` / `stop_play_unit` / `unit_active` / `unit_why` | `systemd-run --unit=torrcast-play --collect`; юнит пользовательский, когда мы не root, и системный, когда root (так будет на стенде из `install.sh`) |
| Тело показа | `cli._cmd_worker` (`--play-key`, скрытый) | ExecStart юнита: TorrServer → ffmpeg → https → приёмник → сторож; всё, что нужно знать о показе, лежит в записи состояния |
| Сторож | `cli.Watch` | раз в 10 с позиция приёмника → state (tmp + rename), абсолютная (`offset + pos`), на 95 % — «досмотрено» |
| Состояние | `state.Entry.advance` / `resumable` / `State.find` / `latest` | фильму пометка + сброс, сериалу следующая серия (этап 4); поиск записи по запросу, без Prowlarr |
| Resume | `cli._resume` | «остановились на H:MM:SS. Продолжить? [Да/сначала]», старт с `-ss pos`, вопросов о релизе и дорожке нет |
| Управление | `cli._cmd_stop` / `_cmd_status` | `stop` гасит юнит (позицию дописывает сам юнит по SIGTERM), `status` читает живой юнит + state |

Плюс две правки оркестратора отдельным коммитом (`d60b782`), см. ниже.

Раздача `Moana 2 (2024).mkv`, 3.1 ГБ, h264 + 3 дорожки, длительность **5977.6 с**.

### 3. `stop` и фиксация позиции

```

остановлено: «Моана 2» на 0:11:04 / 1:39:37     (0.42 с)
state: pos=664.54  dur=5977.57  done=False
```

Последний тик сторожа был на 661 с, в state лёг **664.54 с** — это дописал сам юнит
по SIGTERM, через `finally`. Ничего не потеряно.

### 4. Resume: вопрос, старт, и правда ли с того места

```
$ cast моана 2
«Моана 2» остановились на 0:11:04. Продолжить? [Да/сначала]:
▶ «Моана 2» · дорожка 1 · с 0:11:04 → ТВ   (старт 11 с)
```

| Что | Значение |
|---|---|
| старт resume | **11.4 с** (бюджет §3.1 — 5–15 с) |
| поиск в Prowlarr | не выполнялся |
| вопросы о релизе и дорожке | не задавались (взяты из state) |

**Проверка по кадрам.** Первый кадр первого сегмента возобновлённого показа
(`/dev/shm/torrcast/index0.ts`) сопоставлен с кадрами исходного файла, снятыми прямо
из потока TorrServer с шагом 1/25 с (метрика — PSNR):

| Кадр источника | PSNR с кадром возобновления |
|---|---|
| **661.68 с** | **32.6 дБ** ← максимум |
| 661.72 с | 27.6 |
| 661.60 с | 25.4 |
| 664 с | 17.1 |

Показ возобновился с **661.7 с** при сохранённых 664.54 с — на **2.9 с раньше**.
Это округление `-ss` до ближайшего ключевого кадра (видео идём `copy`, резать
GOP нельзя), укладывается в допуск ±10 с. Дальше позиция шла абсолютной:
`0:11:04 → 0:12:34 → 0:12:58` за 20 с наблюдения, то есть сторож прибавляет offset,
а не считает от нуля возобновлённого потока.

## Правки оркестратора (коммит `d60b782`) — и что они дали живьём

**a. Дефолт релиза.** Кандидат в дефолт = H.264 по имени **или** (кодека в имени нет)
HD-источник `WEB-DL/BDRip/WEBRip/HDTV/Remux…` либо качество ≥720p; DVDRip и CAM без
кодека кандидатами не считаются. Из кандидатов исключаются релизы с оценочным
битрейтом > 20 Мбит/с — в таблице они остаются с ⚠, но Enter их не возьмёт.

Живая выдача по «Моане 2» (134 раздачи): дефолтом стал релиз №1 (1.5 ГБ, 221 сид),
а 2160p на 41.7 ГБ (78 сидов, 27 Мбит/с) и 19.6 ГБ ушли вниз с ⚠. До правки
кандидатов не было вообще — правило «H.264 И ≥720p» на этой выдаче не срабатывало
ни разу (открытый вопрос 2 из stage2.md закрыт).

**b. Проверка настоящего кодека после ffprobe.** Тот самый дефолт оказался ловушкой,
и это видно в логе прогона:

```
Дорожки: читаю поток…
релиз №1 оказался mpeg4 — беру №2

релиз №2: читаю поток…
Файл: Moana 2 (2024).mkv · 3.1 ГБ · 1:39:37 · h264 · ~4.5 Мбит/с
```

Самый обсиженный релиз действительно оказался MPEG-4 (то есть XviD-семейство —
ровно то, чего опасался stage2.md), и цепочка честно перешла к следующему кандидату.
Попыток максимум три, дальше код 1 со списком того, что попалось. Молчаливых
подмен нет (§1): каждая замена — строка в консоли.

## Решения и почему именно так

### 1. Юнит пользовательский или системный — по тому, кто мы

`systemd-run --user` требует живого user-manager; на стенде `install.sh` работает
от root, и там правильнее системный transient-юнит. Поэтому одна строка:
root → системный юнит, не root → `--user`. Ничего постоянного не ставится и не
`enable`-ится ни там, ни там — юнит существует только на время показа, `--collect`
убирает его и в случае падения.

### 2. Юнит знает про показ ровно одно — ключ состояния

`ExecStart` — это `python -m torrcast.cli --play-key movie:моана-2:2024`. Magnet, файл,
дорожка и позиция берутся из записи §4. Отсюда бесплатно получается resume (позиция
уже там), стык серий на этапе 4 (меняется поле `episode`) и отсутствие второго
формата «параметров показа». В юнит пробрасываются `TORRCAST_CONFIG`/`TORRCAST_STATE`,
иначе dev-прогон уехал бы на прод-пути.

### 3. Позиция пишется юнитом, а не командой `stop`

`cast stop` = `systemctl stop`, то есть SIGTERM юниту и ожидание его смерти. Внутри
юнита SIGTERM превращается в исключение, проходит через `finally` и дописывает
позицию (в прогоне: тик на 661 с, в state — 664.54 с). Альтернатива — опрашивать
приёмник из `stop` — означала бы второй клиент к тому же ресиверу и гонку за то,
кто запишет позже.

### 4. Два новых поля в записи состояния

* `query` — slug исходного запроса. Resume обязан найти запись **до** поиска
  (иначе бюджет 5–15 с не выполним), а ключ состояния строится из канонического
  названия, которое известно только после Prowlarr. Сравнение идёт по сохранённому
  запросу и по slug из ключа; чужая картина не подхватывается.
* `done` — «досмотрено». Без него сброшенная в ноль позиция неотличима от «ни разу
  не смотрели», а фильм после финальных титров спрашивал бы «продолжить?».

### 5. Порог 95 % считается от длительности из ffprobe, а не от манифеста

Приёмник отдаёт `dur` как длину того, что уже упаковано (это нужно, чтобы
придерживать упаковку). Настоящая длительность фильма известна из `ffprobe` и
лежит в записи — по ней и считается порог. Иначе «досмотрено» наступало бы через
несколько секунд после старта.

### 6. 🔴 Хвост HLS: один сегмент может пропасть у клиента, и это не наш код

При сквозных прогонах на синтетическом 20-секундном ролике декодер иногда
заканчивал на 16 с из 20 — молча, без единой строки в логе. Разбор:

* воспроизводится **на голом `python -m http.server`**, без нашей раздачи, без TLS,
  без mock'а — то есть это поведение hls-демуксера ffmpeg, а не наша ошибка;
* воспроизводится только в узком окне: пауза 0.2 с между появлением манифеста и
  запуском клиента — обрыв; 0 / 0.5 / 1.5 с — полные 20.04 с;
* причина: `#EXT-X-ENDLIST` приезжает в той же перезагрузке плейлиста, что и
  последний сегмент, и клиент заканчивает на предыдущем.

Цена на ТВ — последние ≤4 с фильма, на порог «досмотрено» (95 %) это не влияет:
в живом прогоне хвоста декодировано 361 из 361 с. В тестах допуск ровно один
сегмент (`HLS_SEGMENT_SECONDS`), потерю середины он не маскирует — этап 2 ловил
пропажу 48 с, это 12 сегментов.

## Открытые вопросы

1. **`--release N` и подмена по кодеку.** Сейчас проверка настоящего кодека работает
   и при явном `--release N`: если указанный релиз оказался не h264, цепочка честно
   переходит к следующему кандидату. Для скриптов это означает, что `--release`
   не гарантирует именно тот релиз. Альтернатива — при явном указании только
   печатать предупреждение и играть что просили. Нужно решение оркестратора.
2. **Ключ состояния и год.** `Picture.key` подставляет `0`, когда года в раздачах нет
   (`movie:название:0`). Пока безобидно, но на стенде две картины без года с
   одинаковым названием сольются в одну запись.
3. **`status` показывает свежайшую запись, а не запись играющего юнита.** Если юнит
   жив, а рядом руками правили state другой картины, строка соврёт. Точный вариант —
   класть ключ показа в `--description` юнита и читать его оттуда; это ~5 строк,
   но пока не понадобилось.
4. **Порог 95 % для сериалов проверен только на переходе записи** (`advance()` даёт
   следующую серию); автопереход показа — этап 4.
5. **Реальный Chromecast позицию отдаёт `media_controller.status`** — ветка написана,
   но, как и весь ТВ-путь, проверяется только на этапе 6.
